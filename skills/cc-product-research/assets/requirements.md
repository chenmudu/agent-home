# 需求回归表

用户原话逐条转成可打勾的验收项。**改版前建表，交付前逐条核对**——这是防“重写丢章节”的唯一可靠办法。

## 表结构

| # | 用户原话（摘） | 转成的验收项 | 落在报告哪里 | 状态 |
|---|---|---|---|---|

状态只有三种：`✅ 已满足` / `⏳ 部分` / `❌ 缺失`。交付前不允许出现 ❌ 而不说明。

## 读者验收（交付前，必做）

交付前由一个没参与调研的 reader（subagent / 新会话）完成三段验收。reader 只拿对应材料，不拿源码、不拿对话记录。

### 第一段：只看第一屏

| # | 问题 | 只看简报能答吗 | 答不出时改哪里 |
|---|---|---|---|
| Q1 | 它是什么？ | | 一句话：改成大白话，≤120 字 |
| Q2 | 给谁用？谁不该用？ | | `who` |
| Q3 | 怎么用？最短路径是什么？ | | `how` |
| Q4 | 代价是什么？ | | `cost` |
| Q5 | 本次没做到什么？ | | `notdone`，不能为空 |
| Q6 | 该不该试？ | | `try`，必须带一句理由 |
| Q7 | 下一步做什么？ | | `next`，必须是一个可执行动作 |

任何一项答不出，先改第一屏，不许让读者往下翻。

### 第二段：只读第 1–5 幕，复述主线

用自己的话复述五件事：

1. 装完多了什么？
2. 输入从哪来？
3. 经过哪些状态？
4. 输出是什么、怎么确认？
5. 谁持有状态、中断后怎么恢复？

### 第三段：读一个功能档案 + 证据附录，复述 3 个事实

- 发生了什么？
- 数字是多少？
- 为什么？

同时圈出所有看不懂的词：影响判断的词补一句人话，不影响判断的改成描述或删掉。

### 规则

- reader 只拿对应材料；拿源码、拿对话记录都不算独立验收。
- 三段答案写进 `appendix-selfproof`，格式见下。
- 三段都过，需求回归表里的 ✅ 才算数。
- 没有独立 reader 时至少隔 10 分钟重读；自己读不算验收。

```text
[读者验收] 第一屏 Q1 → A1 … Q7 → A7；主线 M1 → A1 … M5 → A5；
证据 F1 → A1 … F3 → A3；未解释词：<词 or 无>
```

## 已完成的实例

> 下表早于 v3 规则，保留作历史示例。新报告必须在 `appendix-selfproof` 补 `[读者验收]`，不能只沿用旧表。

| # | 用户原话（摘） | 转成的验收项 | 落在报告哪里 | 状态 |
|---|---|---|---|---|
| 1 | 三个项目的定位、内容、功能、核心理念 | 每个对象要有独立定位段 + 理念段 | 逐项目深档 + 理念章 | ✅ |
| 2 | 总结重复的功能和差异点 | 重复与差异各成一章，且都要有对比图 | §2.1 / §2.2 | ✅ |
| 3 | 架构清晰、功能齐全、对比清晰、来源准确 | 章节导航可跳转；每条结论带出处 | 导航 + 全文引用 | ✅ |
| 4 | 专业名词需要深度解释 | 术语按“人话→定义→为什么重要”三段写 | §1.1 | ✅ |
| 5 | 配一些图，不要干巴巴 | 每个核心论点至少一张图 | 18 张编号图 | ✅ |
| 6 | 先产品，后技术，然后才是细节 | 每章开头先写用户得到什么 | 各章 h4「产品视角」 | ✅ |
| 7 | 自己 review，确认哪里不够好，再改 | 交付前有一轮自审 + 实际改动清单 | 修订记录 | ✅ |
| 8 | 揉成一个产品，喜欢的留、不喜欢的砍 | 取舍表每行有 留/改/砍/增 + 代价 | §3.2 | ✅ |
| 9 | 设计、架构、产品、语言必须统一 | 技术栈统一表 + ADR | §3.4 / §3.5 | ✅ |
| 10 | 点击查看时不要改变任何内容，删除是绝对限制 | 全程零写操作 + 前后自证 | 附 A + 附录 | ✅ |
| 11 | 截图归档，文档可引用 | 每张截图有编号 + 正文或附录引用 | 附 B | ✅ |
| 12 | 先梳理 → 评审 → 设计 → 构建 | 四个阶段在导航与正文成段 | 导航 + §0/§2/§3/§4 | ✅ |

## 用法

1. 开工时把用户历史原话（含之前会话的）粘进第 2 列，逐条转写；
2. 每写完一幕，回填“落在哪里”；
3. 交付前做三段读者验收；答不出先改报告，不要改验收表；
4. 交付前扫一遍：有 ⏳ 就补，有 ❌ 就问用户是否放弃；
5. 新需求追加在原表下方，不改历史行。
