# 报告骨架（v7）

> v7：一页决策简报 + 五幕运行链 + 证据附录。
> 演进：v5 把结论前置、证据后置；v6 加入可读性验收与“源码是一等证据”；v7 把正文按运行链重排为五幕，并把简报、自证、证据拆成三个附录。

这份文件是报告规则的唯一事实源（SSOT）。`SKILL.md` 只做摘要，不复制全文；两者冲突时以本文为准。

## 1. 语言纪律

- 先用一句大白话讲清“它是什么”，再给结构化版本。
- 一句话 ≤120 字，不含路径、函数名、机制名；不用箭头代替解释。
- 术语首次出现必须解释（人话 → 定义 → 用户为什么该在意）。
- 术语表触发条件：同一个机制名 / 字段名 / 内部代号在正文出现 ≥2 次，或只出现一次但影响结论、代价或下一步。
- 术语表 ≤5 行，一行一句人话 + 它为什么影响判断；不解释 `API`、`CLI` 这类通用词。术语表放在简报之后，不占第一屏。
- KPI 标签自解释，写清“数字指什么 + 统计范围”，例如“15 个顶层命令 · 50 个可执行叶子命令”，不写 `15 · 50`。
- 数字一律带口径（累计 / 快照 / 单次请求）+ 取证日期；口径不同的数字不相减、不相加、不比倍数。
- 结论先行，不写“值得注意的是”“总的来说”。

## 2. 证据标签

实机结论前标来源：`[浏览器]` `[屏幕]` `[终端]` `[API]` `[源码]` `[文档]`。

- 不同驱动不互相顶替：屏幕截图证明不了 DOM 行为，接口响应证明不了界面长什么样，源码证明不了可达性与 UX。
- 源码 / 文档是一等证据，不是“降级”；但源码-only 报告必须在第一屏写“未实机”，并在 `appendix-selfproof` 的「访问面与驱动」复述用了哪个驱动、哪些结论只来自源码。
- 每条结论能指回一次操作、一张截图、一行代码或一份文档；指不回就标“未验证”。

## 3. 视觉基准（硬规则）

- **结构固定，皮肤取自对象。** 版式（简报、五幕、表格、折叠图、证据标签）由本 skill 固定；配色、字体气质、圆角、密度从**被调研对象的 UI** 取样——报告读起来应该像那个产品的文档，不像模板。
- 取样方法：先截对象的首屏 + 一个详情页，取 3 个色（背景 / 面板 / 主强调色）+ 字体气质（等宽还是人文、圆角大小），再映射到 `--sk-*` 变量。
- `<style>` 顶部必须写明皮肤来源：`/* skin: <对象名> UI */`。没写就等于没声明基准。
- 允许按对象重设变量值，不允许改组件结构（简报、五幕、附录、编号、表格语义）。
- 五幕是**状态链**，不是五个并列章节；正文按时间线和数据流推进。
- 窄屏：≤900px 正文在前、导航在后；≤700px 页面无横向溢出，宽表在自己的框内横向滚动，`pre` 不超宽，`code` 可任意断行。
- 1280×800 第一屏不滚动应能看到标题、元信息表、决策简报的 7 行。

## 4. 文件与命名（硬规则）

```
<workspace>/.research/<slug>/<YYYY-MM-DD>-v<N>.html
<workspace>/.research/<slug>/index.json
```

- `slug`：仓库名小写，非 `[a-z0-9]` 转 `-`（`context-lens`、`agent-trace-viewer`）；撞名时用 `--slug` 人工区分。
- `N`：这个对象的第几次调研，由目录里已有报告决定，不由本次心情决定。
- **永不覆盖已有报告**：同一天再调研也是 `-v2.html`，不是改写 `-v1.html`。报告是证据，覆盖等于销毁证据；版本之间的差异本身就是再调研最有价值的部分。
- 再调研时 `v≥2` 必须带「本版变化」块、`report-meta.previous`，以及**逐条复检**（见 §6）。
- 用户指定 `--out` 时从其指定，但 `index.json` 仍要登记。
- `index.json` 里的相对路径统一用 `/` 分隔（写入时显式转换）。

## 5. 页首元信息（固定六行表）

`<table class="meta">`，标签列固定、顺序固定，值只填事实：

| 标签 | 值 |
|---|---|
| 调研对象 | `owner/repo`（本地项目写绝对路径；商业产品写产品名 + 官网） |
| 版本 / 提交 | `v0.8.0 · ce17b9d (2026-10-21)`；缺失写 `—` |
| 报告版本 | `v2 · 第 2 次调研 · 上一版 2026-10-29`；首次写 `v1 · 首次调研` |
| 本地克隆 | 绝对路径，没有写 `—` |
| 调研方式 | `实机操作 + 受控实验 + 源码`（按实际，多选） |
| 调研日期 | `YYYY-MM-DD` |

不允许把六行压成两行 `·` 串——标签是为了让人和机器都能一眼定位字段。

## 6. 本版变化（v≥2，放 `appendix-selfproof`）

第一屏只留一句“相比上一版变了什么”；完整 delta 块放 `appendix-selfproof` 的「本版变化」，固定六条：

```
对象版本：旧 → 新
结论是否翻转：是 / 否 + 一句为什么
新增功能：
消失 / 失效功能：
逐条复检：v1 的每个功能块 → 仍成立 / 已变化 / 未复查（逐条，不许合并成一句）
被推翻的旧结论：没有就写“无”
```

- 首次调研写“首次调研，无上一版”。
- **复检不是重读旧报告。** “结论未翻转”必须建立在“这次重新验过”之上；没复查就写“未复查”并说明原因。上一版最硬的缺陷不许悄悄消失。

## 7. 前置简报（第一屏，7 行）

### 7.1 固定结构

```html
<section id="brief" class="verdict brief">
  <h2 class="brief-h">决策简报</h2>
  <p class="one"><strong>一句话：</strong>它是什么，大白话，≤120 字</p>
  <div class="brief-grid">
    <div class="brief-row"><div class="k">给谁用</div><div class="c" data-k="who">谁在什么场景用；谁不该用</div></div>
    <div class="brief-row"><div class="k">怎么用</div><div class="c" data-k="how">最短路径；不贴代码块</div></div>
    <div class="brief-row"><div class="k">代价</div><div class="c" data-k="cost">钱 / 时间 / 风险 / 不可逆动作</div></div>
    <div class="brief-row"><div class="k">本次没做到</div><div class="c" data-k="notdone">未实机 / 未验证 / 没权限；没有就写“无”</div></div>
    <div class="brief-row"><div class="k">该不该试</div><div class="c" data-k="try">采纳 / 试用 / 观察 / 放弃 + 一句理由</div></div>
    <div class="brief-row"><div class="k">下一步</div><div class="c" data-k="next">一个可执行动作</div></div>
  </div>
  <div class="kpis">
    <div class="kpi"><div class="v">15</div><div class="l">15 个顶层命令 · 50 个可执行叶子命令</div></div>
    <div class="kpi"><div class="v">3</div><div class="l">3 条主链路 · 来自 2 次实机操作</div></div>
    <div class="kpi"><div class="v">6</div><div class="l">6 个功能档案 · 覆盖 4 个状态节点</div></div>
  </div>
</section>
```

### 7.2 顺序与硬规则

| 顺序 | 行 | `data-k` | 必须回答 |
|---|---|---|---|
| 1 | 一句话 | 无（`<p class="one">`） | 它是什么，大白话，≤120 字，不含路径/函数名/机制名 |
| 2 | 给谁用 | `who` | 谁在什么场景用；谁不该用 |
| 3 | 怎么用 | `how` | 最短路径；不贴代码块 |
| 4 | 代价 | `cost` | 钱 / 时间 / 风险 / 不可逆动作 |
| 5 | 本次没做到 | `notdone` | 未实机 / 未验证 / 没权限；没有就写“无” |
| 6 | 该不该试 | `try` | 采纳 / 试用 / 观察 / 放弃 + 一句理由 |
| 7 | 下一步 | `next` | 一个可执行动作 |

- 简报内不得出现 `<pre>`、`<table>`、`<img>`、`<details>`。
- `notdone` 不得为空。
- `report-meta.verdict.oneLine` 必须与简报第一行同一句。
- 简报内恰好 3 个 KPI 磁贴，每个必须有 value 和 label；`label` 必须写清“数字指什么 + 统计范围”，不能只写 `15 · 50`。
- 简报在第一屏内读完；术语表放在简报之后，不占第一屏。

### 7.3 读者模式

从决策句推断，不额外提问。脚手架默认 `evaluator`。

| 模式 | 判据 | 第一屏重点 | 正文展开 |
|---|---|---|---|
| `evaluator` | 要不要用 / 选哪个 | 结论、代价、适合谁 | 五幕 + 主线上 3 个关键功能档案；另 3 个进证据附录（总 ≥6） |
| `operator` | 怎么装 / 怎么跑 / 怎么排障 | 最短路径、失败路径、回滚 | 第一、二、三幕展开；功能档案 ≥6（可短） |
| `maintainer` | 怎么改 / 怎么接 / 会不会坏 | 机制、边界、维护成本 | 五幕 + 6 个功能档案 + 15 处源码引用 + 6 个文件 |

读者模式只改变“先讲什么、讲多深”，不降低证据下限。

## 8. 五幕（按运行链，不按证据类别）

### 8.1 五幕定义

正文按 `S0 --安装/接入--> S1 --首次运行--> S2 --处理--> … --输出--> Sn` 组织；功能挂在状态节点上，不做独立功能目录。

| 幕 | 回答 | 必须有的动态产物 | 停在哪 |
|---|---|---|---|
| 1 进入 `a1` | 第一次怎么跑起来 | `data-table="first-run"`：宿主/平台 → 前置条件 → 安装/接入 → 第一条命令 → 第一个可见结果 → 卡点 | 读者能照着走到第一个可见结果 |
| 2 安装后 `a2` | 环境里多了什么，带来什么 | `data-table="delta"`：宿主/平台 → 新增资产 → 被激活的能力 → 好影响 → 代价/坏影响 → 没变的东西 → 回滚 | 能说清“装了什么、变了什么、怎么退” |
| 3 核心链路 `a3` | 数据从哪来、经过哪些状态、变成什么 | `data-table="input"` + `data-flow="state"` + `data-table="output"` + 功能档案 | 主链路闭合，输出可验证 |
| 4 承载者 `a4` | 谁维持流程和状态 | `data-table="carrier"`：阶段 → 承载者 → 状态存放 → 谁能读/写 → 中断/恢复 → 清理 | 每个阶段都有 owner、state store、failure path |
| 5 横切 `a5` | 主链路没讲清但影响判断的点 | `data-table="impact"`（四行：`human`/`host`/`object`/`artifact`）+ 未验证表 | 只留会改变判断的点 |

### 8.2 第 3 幕的列定义

| 子段 | 列 |
|---|---|
| 输入 | 输入 → 来源/路径 → 最小单位 → 读什么 → 不读什么 → 权限/隐私 |
| 处理 | `#` → 输入状态 → 执行者 → 处理 → 输出状态 → 失败/降级 → 证据 |
| 输出 | 产物 → 位置/格式 → 怎么确认是真的 → 状态语义 → 误判风险 |

输入必须落到最小单位，例如 `workspace → session → turn → step → operation`，或 `file → symbol → line`，或 `request → field`。

### 8.3 状态链硬约束

```text
S0 --安装/接入--> S1 --首次运行--> S2 --处理--> … --输出--> Sn
```

每一行状态转移必须写清：输入状态 → 谁执行 → 处理 → 输出状态 → 失败/降级 → 证据。

- 状态表至少 3 行（`data-state` 计数 ≥3）。
- 主链路超过 8 跳时，合并不改变判断的中间跳，并在正文说明合并了什么。
- 功能档案挂在状态节点下面，一个功能只在一个主位置讲透，其他位置用 `#fn-N` 锚点。
- 承载者表覆盖每个状态阶段；中断/恢复和清理不能留空。

### 8.4 静态资产规则

任何 `SKILL.md`、配置、manifest、hook 脚本、模板、提示词，只有回答以下四个问题才写进正文：

1. 谁在什么时候读它；
2. 它改变了哪个状态；
3. 没有它，哪个输出/行为会不同；
4. 证据在哪（`路径:行号` / 命令 / 截图）。

答不出就是资产清单里的一行，不是能力；放证据附录或删掉。

## 9. C / D / E 级如何套五幕（同骨架换单位）

- **C 对比 / 选型 / 合并**：五幕骨架不变，单位换成“候选对象”；a1 进入每个候选，a3 用同一把尺子对比输入 → 状态 → 输出，a4 写共存时谁持有状态，a5 写合并冲突。
- **D 外部方案吸收**：a1 先定位“它在我们系统里坐哪个位子”，a2 写引入后多了什么，a3 写可搬的部分与接缝，a4 写谁维护，a5 写不搬的部分与风险。
- **E 失败 / 停更复盘**：a1 写它曾经怎么进入，a2 写环境与分发变化，a3 用状态链写死因分层，a4 写谁持有残留状态，a5 写可复活性与教训。
- 一级只写一段提案，不阻塞；同骨架不等于同深度，证据下限不降。

## 10. 功能档案（三段式）

单位是**一个功能点一块**，不是一段议论。块数 = 功能索引里“实测”的行数；缺一块就等于漏验一个功能。

每块固定三段，顺序不许改：

```
### fn-3 · 丢弃上下文：用户以为在删记录

产品意图
  它想让用户得到什么；用户在这里会假设什么；这个设计的取舍。
  （大白话，禁止出现代码名词）

代码确认
  路径:行号 —— 数据从哪来、谁算出这个数、关键常量是多少。
  边界：拿不到数据时怎么显示；失败时静默还是报错。

判定：属实 / 打折扣 / 只是表面
  一句话说清“设计说的是不是真的”，并指出确认到了哪一行。
```

规则：

- **判定必须出现**，只能三选一。“属实”也要给出确认点；“打折扣”要写清哪一半不成立。
- 产品意图里不许出现函数名、文件名；代码确认里不许只写文件不写行号。
- 每块至少一条证据（图号 / 命令 / 数字），没有就搬去 a5 的未验证表。
- 一块超过 4 段说明混进了两个功能，拆开。
- 同一件事不许在 a5 再讲一遍：a5 只写跨功能的横切结论。
- 功能索引只做索引：一行一个功能，末列 `→ fn-3` 链接到本段；表里只写“入口 / 用户得到什么 / 状态”，不写结论。

## 11. 深度下限 + 广度与深度

交付前硬指标：

- 功能档案 ≥6；少于 6 说明没进到功能粒度，回去补。
- 源码引用 ≥15 处，覆盖 ≥6 个文件（`路径:行号` 计数）；单文件产品可用 `research.singleFile: true` 放宽文件数。
- 宣称/可见/实现表每行有代码引用或“无实现”，不许留空。
- 至少做一次**口径对照**：同一件事在两个地方（两个面板、界面与 CLI、界面与文档）的数字或规则，对不上就是最硬的发现；找不到要写明查过哪几处。
- 状态表 ≥3 行；承载者表覆盖每个状态阶段。
- 这是证据下限，不是引用数 KPI；每多一处引用必须改变一个判断。

广度与深度：

- 广度不降：所有可达入口都要走；源码-only 时用 README / 路由 / 导出 / 命令注册点画入口地图。
- 叙事有预算：正文只留会改变判断的功能和状态；其余进证据附录。
- 深度不降：引用不是 KPI，但没有 `路径:行号` 的机制结论只能算推测。
- 读者模式只改讲法，不改证据；源码是一等模式，不是降级。

## 12. 四件必须品 + 三段读者验收

四件必须品全部放证据附录，第一屏只留一句：

1. **需求回归**（`appendix-selfproof`）：用户原话逐条转成验收项，状态只有 ✅ / ⏳ / ❌。
2. **读者验收**（`appendix-selfproof`）：交付前由独立 reader 完成三段验收，正文写 `[读者验收]`，不能只写在 HTML 注释里。
3. **自我反驳**（`appendix-evidence`）：至少 3 条，格式固定——`先以为 <A>。更正：<B>。证据：<路径:行号 / 截图 / 实测>`。
4. **非变更自证**（`appendix-selfproof`）：

```
操作区间：<开始> → <结束>
写操作：0 次（或：L2 共 N 次，均已撤销）
外部调用：<哪些操作花了钱/额度>
被改动文件：<路径 mtime>（只读交互也会写缓存/索引，必须列）
自证：<关键计数/合计> 开始 = 结束
```

### 12.1 读者验收（三段，交付前必做）

由一个没参与调研的 reader（subagent / 新会话）完成；reader 只拿对应材料，不拿源码、不拿对话记录。

1. **第一屏**：只读简报，回答 7 问；任何一项答不出，先改第一屏，不许让读者往下翻。
2. **主线**：只读第 1–5 幕，用自己的话复述“装完多了什么 → 输入从哪来 → 经过哪些状态 → 输出是什么、怎么确认 → 谁持有状态”。
3. **证据**：读一个功能档案 + 证据附录，复述 3 个关键事实（发生了什么 / 数字是多少 / 为什么），并圈出所有看不懂的词；影响判断的词补一句人话，不影响判断的改成描述或删掉。

记录格式：

```text
[读者验收] 第一屏 Q1 → A1 … Q7 → A7；主线 M1 → A1 … M5 → A5；
证据 F1 → A1 … F3 → A3；未解释词：<词 or 无>
```

三段都通过，需求回归表里的 ✅ 才算数。没有独立 reader 时至少隔 10 分钟重读；自己读不算验收。

## 13. `report-meta` / `index.json`

报告是人读的，同时必须有一块机器可读的元信息，供后续 agent 判断“这个对象查没查过、结论是什么、哪些还没验”。

```html
<script type="application/json" id="report-meta">{ … }</script>
```

`schema: "product-research/report@1"`，字段固定：

| 字段 | 内容 |
|---|---|
| `slug` / `title` | 与目录名、标题一致 |
| `object` | `name` `repo` `version` `commit` `commitDate` `localPath` |
| `research` | `date` `version` `level` `modes` `contractVersion` `reader` `accessSurfaces[]` `degraded[]` `decision` `recheck[]` |
| `verdict` | `oneLine` `kpis[3]{label,value,scope}` `fitFor[]` `notFor[]` |
| `profile` | `positioning` `goal` `status` `problems[]` `approach` `features[]{id,name,intent,mechanism,verdict,evidence}` |
| `claims` | `[{claim, visible, implemented, delta}]` |
| `unverified` | `[{missing, why, impact}]` |
| `selfRefutation` | `[{assumed, corrected, evidence}]`（≥3） |
| `research.recheck` | v≥2 必填：`[{id, claim, status: confirmed|changed|unchecked, note}]` |
| `previous` | `{version, file, date}` 或 `null` |

契约版本：

- `contractVersion >= 3`：五幕 + 三附录；必须显式写该字段，手写报告也一样。
- `contractVersion === 2`：九段 + v2 可读性检查；`reader` / `brief` 是 v3 新增，旧 v2 报告缺失时只给 warn，不判失败。
- 没有 `contractVersion` 或 `< 2`：legacy，只做九段结构校验，不强制简报。

`index.json` 是跨版本登记表（`version / file / date / level / objectVersion / commit / decision / contractVersion / reader`），由 `scripts/new_report.mjs` 维护；skill 开工前读它判断“第几次调研”。相对路径统一用 `/` 分隔。

## 14. 图片纪律

位图截图**默认折叠**，展开是固定尺寸缩略图，点击看原图。

```html
<details class="fig">
<summary>图 3 · 架构页：模型写的组件图 + 代码算的调用图</summary>
<img src="data:image/png;base64,…" width="720" height="480" loading="lazy"
     alt="架构页截图"
     style="width:720px;height:480px;object-fit:contain;background:var(--sk-code);cursor:zoom-in"
     onclick="const w=open('','_blank');w.document.body.style.margin=0;const i=w.document.createElement('img');i.src=this.src;i.style.maxWidth='100%';w.document.body.appendChild(i)">
<figcaption>它证明了：<一句话></figcaption>
</details>
```

规则：

- 固定 `width` / `height` 属性（默认 720×480），CSS 同一尺寸 + `object-fit:contain`，**不要整页宽铺满**。
- 折叠标题必须是 `图 N · 它证明了什么`，读者不展开也知道值不值得看。
- 唯一一份字节：原图靠 `onclick` 读 `this.src` 打开，不要为了“点击放大”再存一份 data URI。
- 全部 `loading="lazy"`。
- SVG 示意图不折叠（矢量、体积小），但仍要编号 + 一句话说明。
- 附录「截图索引」是索引表：`图号 / 内容 / 所在幕`——不再列文件路径（单文件产物没有独立截图）。

## 15. 质量线（交付前自问，20 条）

1. 五幕顺序是不是 `brief → a1 → a2 → a3 → a4 → a5 → 三个附录`？
2. a1 有没有宿主/平台、前置条件、安装/接入、第一条命令、第一个可见结果、卡点？
3. a2 有没有按宿主拆 delta，写清新增资产、被激活的能力、好影响、代价、没变的东西、回滚？
4. a3 的输入有没有落到最小单位（`file → symbol → line` / `request → field`）？
5. a3 的状态表是不是 ≥3 行，每行都有输入状态、执行者、处理、输出状态、失败/降级、证据？
6. a3 的输出有没有产物、位置/格式、怎么确认是真的、状态语义、误判风险？
7. a4 的承载者表是不是覆盖每个阶段，写清 owner、state store、读/写、中断/恢复、清理？
8. a5 的影响矩阵是不是 `human` / `host` / `object` / `artifact` 四行，未验证表非空？
9. 静态资产有没有回答四问？答不出的有没有移到证据附录或删掉？
10. 每个功能是不是只有一个主位置讲透，其他位置用 `#fn-N` 锚点？
11. 第一屏不滚动能不能回答 7 个问题：是什么 / 给谁用 / 怎么用 / 代价 / 本次没做到 / 该不该试 / 下一步？
12. 简报是不是恰好 7 行 + 3 个 KPI，KPI 标签能不能自解释“数字指什么 + 范围”？
13. `notdone` 非空；简报里没有 `pre` / `table` / `img` / `details`？
14. 术语表是不是 ≤5 行、放在简报之后？触发条件是重复 ≥2 次或影响判断吗？
15. 功能档案 ≥6，每块都有“产品意图 → 代码确认 → 判定”，代码确认含 `路径:行号`？
16. 源码引用 ≥15 处、覆盖 ≥6 个文件？每多一处引用有没有改变一个判断？
17. 宣称/可见/实现表的每一行都有代码引用或“无实现”？至少做了一次口径对照？
18. 需求回归、自我反驳 ≥3、非变更自证、本版变化（v≥2）是不是都在证据附录，计数前后一致？
19. `[读者验收]` 是不是在 `appendix-selfproof` 正文里，三段都过了，reader 独立？
20. v2 / legacy 报告还能不能通过旧版九段校验？v3 报告里有没有残留旧版结构术语，或把“没有实例”写成“按宣称处理”的旧写法？
