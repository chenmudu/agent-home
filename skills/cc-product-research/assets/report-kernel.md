# 报告骨架（v3）

## 语言纪律

- 先用一句大白话讲清"它是什么"，再给结构化版本。
- 术语首次出现必须解释（人话 → 定义 → 用户为什么该在意）。
- 结论先行，不写"值得注意的是""总的来说"。
- 数字一律带口径（累计 / 快照 / 单次请求）+ 取证日期。

## 证据标签

实机结论前标来源：`[浏览器]` `[屏幕]` `[终端]` `[API]` `[源码]` `[文档]`。

不同驱动不互相顶替——屏幕截图证明不了 DOM 行为，接口响应证明不了界面长什么样。第 2 段要写清本次用了哪个驱动、哪些结论只来自源码。

## 视觉基准（硬规则）

- **结构固定，皮肤取自对象。** 版式（九段、表格、折叠图、证据标签）由本 skill 固定；配色、字体气质、圆角、密度从**被调研对象的 UI** 取样——报告读起来应该像那个产品的文档，不像模板。
- 取样方法：先截对象的首屏 + 一个详情页，取 3 个色（背景 / 面板 / 主强调色）+ 字体气质（等宽还是人文、圆角大小），再映射到 `--sk-*` 变量。
- `<style>` 顶部必须写明皮肤来源：`/* skin: <对象名> UI */`。没写就等于没声明基准。
- 允许按对象重设变量值，不允许改组件结构（折叠、编号、表格语义）。

## 文件与命名（硬规则）

```
<workspace>/.research/<slug>/<YYYY-MM-DD>-v<N>.html
<workspace>/.research/<slug>/index.json
```

- `slug`：仓库名小写，非 `[a-z0-9]` 转 `-`（`context-lens`、`agent-trace-viewer`）；撞名时用 `--slug` 人工区分。
- `N`：这个对象的第几次调研，由目录里已有报告决定，不由本次心情决定。
- **永不覆盖已有报告**：同一天再调研也是 `-v2.html`，不是改写 `-v1.html`。报告是证据，覆盖等于销毁证据；版本之间的差异本身就是再调研最有价值的部分。
- 再调研时 `v≥2` 必须带「本版变化」块、`report-meta.previous`，以及**逐条复检**（见下）。
- 用户指定 `--out` 时从其指定，但 `index.json` 仍要登记。

## 页首元信息（固定六行表）

`<table class="meta">`，标签列固定、顺序固定，值只填事实：

| 标签 | 值 |
|---|---|
| 调研对象 | `owner/repo`（本地项目写绝对路径；商业产品写产品名 + 官网） |
| 版本 / 提交 | `v0.8.0 · ce17b9d (2026-10-21)`；缺失写 `—` |
| 报告版本 | `v2 · 第 2 次调研 · 上一版 2026-10-29`；首次写 `v1 · 首次调研` |
| 本地克隆 | 绝对路径，没有写 `—` |
| 调研方式 | `实机操作 + 受控实验 + 源码`（按实际，多选） |
| 调研日期 | `YYYY-MM-DD` |

不允许把六行压成两行 `·` 串——标签是为了让人和机器都能一眼定位字段。

## 本版变化（v≥2，紧贴元信息表下方）

`<div class="delta" id="delta">`，六条固定：

```
对象版本：旧 → 新
结论是否翻转：是 / 否 + 一句为什么
新增功能：
消失 / 失效功能：
逐条复检：v1 的每个功能块 → 仍成立 / 已变化 / 未复查（逐条，不许合并成一句）
被推翻的旧结论：没有就写"无"
```

**复检不是重读旧报告。** "结论未翻转"必须建立在"这次重新验过"之上；没复查就写"未复查"并说明原因。上一版最硬的缺陷不许悄悄消失。

## 正文结构：前置卡 + 九段

**前置卡（不编号）**：结论一句话 + 3 个数字（带口径）+ 适合谁 / 不适合谁 + 决策（`采纳 / 试用 / 观察 / 放弃`）。

| # | 段 | 必须回答 |
|---|---|---|
| 1 | **产品画像** | 定位 · 目标 · 现状 · 问题 · 解决方法（五小节；功能不在这里写） |
| 2 | **范围、边界与自证** | 访问面与驱动 · 降级声明 · 需求回归打勾表 · 非变更自证 |
| 3 | **宣称 / 可见 / 实现** | 三列核对表 + 差集解释，每行带代码引用 |
| 4 | **功能地图** | 入口清单 + 功能索引表（一行一个功能，链到第 6 段） |
| 5 | **主旅程实测** | `J1..Jn`：目标 → 操作 → 看到 → 卡在哪 |
| 6 | **功能确认** | 一个功能一块：产品意图 → 代码确认 → 判定（核心段，见下） |
| 7 | **机制、边界与失效** | 跨功能的横切结论：数据流 · 常量总表 · 静默降级 · 维护成本 |
| 8 | **未验证区** | 每条写清"缺什么、错了会怎样" |
| 9 | **待拍板** | 不确定的交给用户，每条附默认建议 |
| 附 | 截图索引 · 源码引用 · 复现命令 | |

C / D / E 级复用同一顺序：第 1 段仍要写画像（对比、吸收、复盘都先要知道它是什么），第 3 段换成该级的对照表（C=横向矩阵，D=座位判断，E=目标验收），第 6 段仍按"设计意图 → 代码确认 → 判定"写，对象换成"候选方案 / 本产品承诺 / 它的原始目标"。

## 第 1 段：产品画像怎么写

五小节，先产品、后其余；答不出来就写"未确认"，不要用功能罗列填空。

| 小节 | 回答 | 证据从哪来 |
|---|---|---|
| 1.1 定位 | 一句话它是什么；替代谁 / 被谁替代；**不是什么** | README 首段 + 首页首屏 + 与相邻产品对照 |
| 1.2 目标 | 它想解决谁的什么问题（引原话）；目标有没有漂移 | README / release note / 首版 issue |
| 1.3 现状 | 版本、活跃度、装机量、维护状态；能给数字就给 | git log / release / 站点 |
| 1.4 问题 | 用户实际撞到什么（issue、报错、自己卡住的地方） | issue 搜索 + 失败态实测；与 1.2 分开写 |
| 1.5 解决方法 | 核心机制一句话 + 为什么这样解 + 付出什么代价 | 源码主链路 + 实测 |

功能细节**不在这段写**——下沉到第 6 段，一个功能一块。

## 第 6 段：功能确认怎么写（核心）

单位是**一个功能点一块**，不是一段议论。块数 = 第 4 段功能表里"实测"的行数；缺一块就等于漏验一个功能。

每块固定三段，顺序不许改：

```
### fn-3 · 丢弃上下文：用户以为在删记录

产品意图
  它想让用户得到什么；用户在这里会假设什么；这个设计的取舍。
  （大白话，禁止出现代码名词）

代码确认
  路径:行号 —— 数据从哪来、谁算出这个数、关键常量是多少。
  边界：拿不到数据时怎么显示；失败时静默还是报错。

判定：属实 / 打折扣 / 只是表面
  一句话说清"设计说的是不是真的"，并指出确认到了哪一行。
```

规则：

- **判定必须出现**，只能三选一。"属实"也要给出确认点；"打折扣"要写清哪一半不成立。
- 产品意图里不许出现函数名、文件名；代码确认里不许只写文件不写行号。
- 每块至少一条证据（图号 / 命令 / 数字），没有就搬去第 8 段"未验证区"。
- 一块超过 4 段说明混进了两个功能，拆开。
- 同一件事不许在第 7 段再讲一遍：第 7 段只写跨功能的横切结论。

第 4 段的功能表是**索引**：一行一个功能，末列 `→ fn-3` 链接到本段；表里只写"入口 / 用户得到什么 / 状态"，**不写结论**。

## 深度下限（交付前硬指标）

- 功能块 ≥ 6；少于 6 说明没进到功能粒度，回去补。
- 源码引用 ≥ 15 处，覆盖 ≥ 6 个文件（`路径:行号` 计数）。
- 第 3 段每一行都要有代码引用；没有实现的写"无实现"，不许留空。
- 至少做一次**口径对照**：找同一件事在两个地方（两个面板、界面与 CLI、界面与文档）的数字或规则，对不上就是最硬的发现；找不到要写明查过哪几处。

## 三件必须品（格式固定）

**需求回归**（放第 2 段）：用户原话逐条转成验收项，状态只有 ✅ / ⏳ / ❌。

**非变更自证**（放第 2 段）：

```
操作区间：<开始> → <结束>
写操作：0 次（或：L2 共 N 次，均已撤销）
外部调用：<哪些操作花了钱/额度>
被改动文件：<路径 mtime>（只读交互也会写缓存/索引，必须列）
自证：<关键计数/合计> 开始 = 结束
```

**自我反驳**（放第 6 段末尾）：至少 3 条，格式固定——

```
先以为 <A>。更正：<B>。证据：<路径:行号 / 截图 / 实测>
```

## Agent 可读（硬规则）

报告是人读的，同时必须有一块机器可读的元信息，供后续 agent 判断"这个对象查没查过、结论是什么、哪些还没验"。

```html
<script type="application/json" id="report-meta">{ … }</script>
```

`schema: "product-research/report@1"`，字段固定：

| 字段 | 内容 |
|---|---|
| `slug` / `title` | 与目录名、标题一致 |
| `object` | `name` `repo` `version` `commit` `commitDate` `localPath` |
| `research` | `date` `version` `level` `modes` `accessSurfaces[]` `degraded[]` `decision` `recheck[]` |
| `verdict` | `oneLine` `kpis[3]{label,value,scope}` `fitFor[]` `notFor[]` |
| `profile` | `positioning` `goal` `status` `problems[]` `approach` `features[]{id,name,intent,mechanism,verdict,evidence}` |
| `claims` | `[{claim, visible, implemented, delta}]` |
| `unverified` | `[{missing, why, impact}]` |
| `selfRefutation` | `[{assumed, corrected, evidence}]`（≥3） |
| `recheck` | v≥2 必填：`[{id, claim, status: confirmed|changed|unchecked, note}]` |
| `previous` | `{version, file, date}` 或 `null` |

`index.json` 是跨版本登记表（`version / file / date / level / objectVersion / commit / decision`），由 `scripts/new_report.mjs` 维护；skill 开工前读它判断"第几次调研"。

## 图片纪律

位图截图**默认折叠**，展开是固定尺寸缩略图，点击看原图。

```html
<details class="fig">
<summary>图 3 · 架构页：模型写的组件图 + 代码算的调用图</summary>
<img src="data:image/png;base64,…" width="720" height="480" loading="lazy"
     alt="架构页截图"
     style="width:720px;height:480px;object-fit:contain;background:var(--sk-code);cursor:zoom-in"
     onclick="const w=open('','_blank');w.document.body.style.margin=0;const i=w.document.createElement('img');i.src=this.src;i.style.maxWidth='100%';w.document.body.appendChild(i)">
<figcaption>它证明了：<一句话></figcaption>
</details>
```

规则：

- 固定 `width` / `height` 属性（默认 720×480），CSS 同一尺寸 + `object-fit:contain`，**不要整页宽铺满**。
- 折叠标题必须是 `图 N · 它证明了什么`，读者不展开也知道值不值得看。
- 唯一一份字节：原图靠 `onclick` 读 `this.src` 打开，不要为了"点击放大"再存一份 data URI。
- 全部 `loading="lazy"`。
- SVG 示意图不折叠（矢量、体积小），但仍要编号 + 一句话说明。
- 附录 A 是索引表：`图号 / 内容 / 所在段`——不再列文件路径（单文件产物没有独立截图）。

## 质量线（交付前自问）

1. 第 1 段五小节是不是都答了？"定位"里有没有写"它不是什么"？
2. 第 6 段的功能块数量够不够？每一块是不是都有"产品意图 → 代码确认 → 判定"三段？
3. 有没有哪个功能只有一行表、没有块？那就是漏验。
4. 代码确认里有没有只写文件不写行号的？有就补到行。
5. 第 3 段的差集有没有被解释？口径对照做没做？
6. 未验证区是不是空话？要能回答"错了会错在哪"。
7. 三条必须品在不在？`report-meta` 填没填全？图片是不是都折起来了？
8. v≥2 时，每个旧功能块是否都给了"仍成立 / 已变化 / 未复查"？
9. 报告的皮肤是不是取自对象，而不是模板默认色？
