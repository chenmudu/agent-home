# 访问面：先决定“怎么碰到它”

调研的第一件事不是读代码，是确认**我能用什么方式碰到这个产品**。形态决定驱动，驱动决定证据的强度。

## 七种形态与对应驱动

| 形态 | 怎么判定 | 首选驱动 | 能拿到的证据 | 主要限制 |
|---|---|---|---|---|
| **Web 页面**（本地或远程） | 有 URL | 浏览器：`browser-use`（外部 Chromium/Edge）或内置浏览器 | 截图 + 可访问性树 + DOM + 网络请求 | 登录墙、跨域 iframe、SPA 路由、标签所有权只在当前回合有效 |
| **桌面 App** | 有窗口、有安装包、无 URL | `computer-use`（屏幕 + 辅助功能） | 截图（语义弱，靠看） | 点位易错、缩放/多屏、自绘与画布控件读不到、平台能力差异 |
| **CLI / TUI** | 有命令、无图形界面 | 终端（Bash） | 命令 + 输出文本 | 没有“界面”概念；要自己构造输入；退出码即证据 |
| **HTTP API / SDK** | 有端点或包 | curl / 脚本 | 请求-响应 | 只反映能力面，不反映产品体验 |
| **混合**（Electron / Tauri 内含 Web） | 打包的 Web 应用 | 优先浏览器（能访问内嵌页或调试口时），否则 `computer-use` | 按所选驱动 | 调试口常被关闭；两套证据不可混用 |
| **只能用自家生态** | 厂商客户端 / 专用协议 / 无公开入口 | 该生态本身 | 截图或日志 | 如实写“只能用 X 访问”，**不伪造界面证据** |
| **源码 / 文档（不可运行）** | 有仓库、有文档，但没有可运行实例 | 文件读取 / git / 静态分析 | `路径:行号` + 声明 + 数据流 | 不能证明可达性 / UX；入口要从 README、路由、导出、命令注册点反推 |

**同一产品可能有多个访问面**（例：Web UI + CLI + HTTP API）。先选**用户主路径那一个**，其余作为补充证据，并在报告里区分。没有可运行实例时，源码 + 文档是合法访问面，不写“降级”。

## 四条规则

1. **先探针，再承诺。** 开工前跑一次最小探针，确认驱动真的能用：

   | 驱动 | 探针 |
   |---|---|
   | 浏览器 | 能列出页面 / 能打开目标 URL 并读到标题 |
   | computer-use | 能列出窗口 / 能截到目标窗口 |
   | 终端 | `<cmd> --help` 有输出 |
   | API | `curl -s -o /dev/null -w '%{http_code}'` 拿到状态码 |
   | 源码 / 文档 | 能读 README，且能找到至少一个入口定义（路由 / 导出 / 命令注册点 / CLI help） |

   探针失败就**改用**可行访问面，不要“以为能点”，也不要把它写成“降级”。

2. **每个结论标注驱动。** 浏览器证据、屏幕证据、终端输出、API 响应、源码、文档，可信度不同，必须分开标：
   `[浏览器]` `[屏幕]` `[终端]` `[API]` `[源码]` `[文档]`。

3. **不跨驱动补证。** 不能用屏幕截图证明 DOM 行为，不能用接口响应证明界面长什么样，也不能用源码证明可达性 / UX。

4. **界面说的话优先于我的推断。** 有实机就看实机；没有实机，源码能确认的入口与行为优先于文档，文档优先于自己的推断。源码-only 的能力写“源码可见，未实机”。

## 平台差异（写进 `appendix-selfproof` 的「访问面与驱动」）

- **Windows / macOS / Linux 的 computer-use 能力不同**：辅助功能树的完整度、权限弹窗、DPI 缩放、多屏坐标都会影响点位准确性。
- **浏览器驱动依赖连接器**（Qoder Browser Connector + 扩展在线）。没有连接器时只能让用户手工截图，改用 L0，并声明“实机证据由用户提供”。
- **移动端 / 无公开入口的产品**：默认不做，除非用户提供可用入口。
- **源码 / 文档**：入口定义可能分散在 README、路由表、导出清单、命令注册点；平台差异只能从条件分支和文档里反推，标“源码可见，未实机”。

## 失败与改用

| 情况 | 处置 |
|---|---|
| 连接器不可用 | 让用户手工截图 + 口述操作；报告标“实机证据由用户提供” |
| App 无辅助功能树 | 只用截图，结论限定在“看起来”；行为结论标“未验证” |
| 登录墙 / 验证码 | 请求人工接管（handoff），**不要索取凭据** |
| 只有 API / SDK | 按 D 级（外部方案吸收）处理，不假装有产品界面 |
| **只有源码 / 文档（无实例）** | 走源码 + 文档；第一屏写“未实机”；能力写“源码可见，未实机”；不得推断 UX |
| 产品起不来 | 改用源码 + 文档，不是失败；在「访问面与驱动」写清哪些结论只来自源码 |

## 在简报里怎么写

```
访问面：<形态> / 驱动：<browser-use | computer-use | 终端 | curl | 源码读取> / 探针：<通过 | 失败→改用为何>
```

源码-only 示例：

```
访问面：源码 + 文档（不可运行） / 驱动：源码读取 /
探针：通过（读到 README 与至少一个路由/导出/命令注册点） / 备注：本次未实机
```

报告 `appendix-selfproof` 的「访问面与驱动」必须复述这一行，并说明哪些结论只来自源码、哪些来自实机、哪些未验证。
