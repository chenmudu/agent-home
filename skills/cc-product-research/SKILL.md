# 产品调研

## 这是什么

把一次调研做成一份**能拍板、能复核**的报告：第一屏是一页决策简报（7 问），正文按运行链分成五幕，证据、自证、引用放三个附录。不是功能罗列，也不是审计底稿。

## 最短用法

```
/cc-product-research <代码路径或仓库地址> [产品地址]
```

其余都不必写。下面这些是默认值：

- **只读**：不写、不删、不重建、不发消息；会花 LLM 额度或写盘的动作，开工前问一次。
- **范围**：所有可达入口都要走一遍，不只主路径；能点的点，不能点的追到源码注册点。有可运行实例就实操；没有实例就下载/克隆仓库，基于源码 + 文档调研——这是一等模式，不是降级。
- **产物**：`<workspace>/.research/<slug>/<YYYY-MM-DD>-v<N>.html`，单文件、截图内嵌；可用 `--out` 覆盖。
- **读者模式**：`evaluator`（默认）；要装/跑用 `operator`，要改/接用 `maintainer`。

## 什么时候用

- "调研一下 / 研究一下 / 看看这个仓库 / 这产品怎么样"
- 在多个同类实现之间选型、合并、替代
- 评估一个外部思路或实现值不值得吸收
- 诊断一个产品/仓库为什么坏、还能不能用
- 自查自有产品：宣称的能力是否真的在界面上、真的在代码里

不用于：逆向工程（另一个学科）、纯代码 review、纯竞品情报收集。

## 五条不可协商

1. **默认只读。** 不改变被调研对象的状态；不可逆操作（删除/发布/扣费/改共享配置）永不执行。
2. **不发明规则。** 没被用户确认过、也没在本次证据里出现的检查项，只能当候选，不写进结论。
3. **可追溯。** 每条结论能指回一次操作、一张截图、一行代码或一份文档；指不回就标"未验证"。
4. **先理解再相信。** 第一屏必须回答 7 问：是什么 / 给谁用 / 怎么用 / 代价 / 本次没做到 / 该不该试 / 下一步；术语首次出现解释；交付前由独立 reader 做三段验收（第一屏 7 问 / 五幕主线复述 / 证据 3 个事实复述），答不出先改报告。
5. **按运行链写。** 正文按 `S0 → S1 → … → Sn` 组织；每一跳写输入状态、执行者、处理、输出状态、失败/降级、证据；静态资产必须回答四问，否则不进正文。

## 双镜头（核心）

任何一条发现都要过两个镜头，完整方法见 `references/dual-lens.md`：

- **产品镜头**：谁用、什么场景、看到什么、得到什么、付出什么代价。
- **开发镜头**：靠什么机制、数据结构是什么、边界在哪、怎么坏、维护成本多大。

对齐规则：

- 一条结论只能落在一个镜头里 → 还没查透，回去补另一侧。
- 开发问题必须翻译成产品后果（例：600 行无构建 → 删除按钮一点就 409）；翻译不出来就降权。
- 产品承诺必须找到代码落点（例：界面有筛选 → 哪个函数实现）；找不到就写"无实现"。
- 呈现顺序永远是**产品在前、代码在后**：代码是证据，不是提纲。
- **没有界面时**，"看到"指 README / 文档 / 代码入口能确认的承诺；UX 细节答不出就标"未实机"，不要用源码假装界面。

## 三列核对

每个核心能力填三列，**差集就是报告的价值**：

| 宣称 | 可见 | 实现 |
|---|---|---|
| README / 文案怎么说 | 界面上真的有什么 | 代码里真的做了什么 |

三者不一致时，取证顺序是：先信界面（它是用户的真相），再看文档，最后才是自己的理解；没有界面时，先信"源码能确认的入口与行为"，文档次之。

## SOP：A → B → C → D → E

逐级加深，**每级都能独立交付**，到"能判断"就停。详见 `references/sop-abcde.md`。

| 级 | 回答 | 主要取证 |
|---|---|---|
| **A 产品能力** | 它能干什么、好不好用 | 所有可达入口各走一遍 + 截图 + 五张清单 |
| **B 技术机制** | 怎么做到、边界在哪、会坏在哪 | 源码链路 + 最小复现 |
| **C 对比/选型/合并** | 几个怎么选、能不能并 | A+B 各做一遍 + 同一把尺子 + 共存冲突 |
| **D 外部方案吸收** | 值不值得抄 | 先定位座位，再批判，再小实验 |
| **E 失败/停更复盘** | 为什么坏、还能不能救 | 时间线 + issue/PR 考古 + 版本漂移 |

- **A 级覆盖所有可达入口**，不设上限；另选 3–5 条主路径深入。
- **A 级先行**：先交一页简报（7 问），再交完整证据。
- **源码 A 级**：README / CLI help / 路由 / 导出 / 命令注册点就是入口；每个入口追到 `路径:行号`，能力写"源码可见，未实机"。
- 进入新的一级时，先写**一段提案**（做什么 / 取什么证 / 产出什么），然后继续，不等待确认；同一级内部连续做，不打断。

## 取证

四层证据，越靠上越先做，详见 `references/evidence-rules.md`：

1. 实机操作（点了什么、发生了什么）
2. 截图（可复核的画面）
3. 界面自己说的话（文案 / 空状态 / 报错 / 忙时提示）
4. 源码（用来回答"为什么 / 边界 / 会坏在哪"）

硬规则：

- 能跑的实例必须实操；没有实例时，源码 / 文档是一等证据，不写成"降级"。
- **源码-only** 标 `[源码]`，第一屏"本次没做到"写"未实机"；不得用源码推断 UX。
- 安全 / 边界类结论必须实测，或标"未实测"。
- 第 5 幕「未验证与待拍板」必须存在且非空。

## 访问面（先决定怎么碰到它）

形态决定驱动，驱动决定证据强度：

| 形态 | 驱动 | 能拿到的证据 |
|---|---|---|
| Web 页面 | 浏览器（browser-use / 内置） | 截图 + 可访问性树 + DOM + 网络 |
| 桌面 App | computer-use | 截图（语义弱，靠看） |
| CLI / TUI | 终端 | 命令 + 输出文本 |
| API / SDK | curl / 脚本 | 请求-响应 |
| 混合（Electron / Tauri） | 浏览器或 computer-use | 按所选驱动；两套证据不可混用 |
| 只能用自家生态 | 该生态本身 | 截图或日志；不伪造界面证据 |
| **源码 / 文档（不可运行）** | 文件读取 / git / 静态分析 | `路径:行号` + 声明 + 数据流 |

规则：**先探针再承诺**（列出页面 / 列出窗口 / `--help` / 状态码 / 读到 README 与至少一个入口定义），失败就**改用**可行访问面；每条实机结论标驱动 `[浏览器] [屏幕] [终端] [API] [源码] [文档]`；**不同驱动的证据不能互相顶替**；源码不能证明可达性/UX。混合与只用自家生态的产品按 `references/access-surfaces.md` 处理。

## 开工闸门（整个调研只问一次）

第 0 步不算提问：**先看这个对象查过没有。** 读 `<workspace>/.research/<slug>/index.json`（或用 `scripts/new_report.mjs` 自动判定）——第一次生成 v1，第二次起生成 v2/v3，**永不覆盖旧报告**；再调研必须带「本版变化」块。

然后先在回复里写**六行简报**（决策句 / 对象 / 证据来源 / 许可 / 读者模式 / 产出），然后：

- **只有三种情况停下来提问**：① 决策句推不出；② 要花 LLM 额度或写盘——**指对象那一侧**，写你自己的报告不算；③ 产出位置或形态有歧义。
- 其余情况写完简报直接开工，不等待确认。
- 进入新的 SOP 级（C / D / E）时只写一段提案，不阻塞。

读者模式只有三个值：`evaluator` / `operator` / `maintainer`；默认 `evaluator`。**默认源码调研**：没有可运行实例时，下载/克隆仓库，基于源码 + 文档调研，不写成"降级"。

模板见 `assets/research-brief.md`。操作许可见 `assets/permission-ladder.md`：默认 L0 浏览 + L1 无害交互；L2 需逐次授权；L3 永不执行。**L1 也可能落盘**（缓存、索引、日志），收尾要查。

## 交付

产物是**一个自包含的 HTML**，路径由对象和版本决定：

```
<workspace>/.research/<slug>/<YYYY-MM-DD>-v<N>.html
<workspace>/.research/<slug>/index.json
```

用脚手架生成，不要手抄样式：

```bash
node scripts/new_report.mjs --slug <kebab-case> --title "<name>" \
  --repo <owner/repo> --version <vX> --commit <sha> \
  --commit-date <YYYY-MM-DD> --local "<path>" \
  --level <A|B|C|D|E> --modes "<mode1,mode2>" \
  --reader evaluator|operator|maintainer --root <workspace>
```

它负责：命名与版本号判定、内联结构基线、六行元信息表、**决策简报 + 五幕骨架 + 三个证据附录**、`report-meta` 空壳、`index.json` 登记。之后只填内容。

四条硬规则（细节见 `assets/report-kernel.md`）：

1. **命名**：`<slug>/<date>-v<N>.html`；`N` = 该对象已有报告数 + 1，**永不覆盖**。改报告 = 出新版本，旧版留着当证据。
2. **视觉**：结构固定，皮肤取自被调研对象的 UI（背景 / 面板 / 主色 / 字体气质），在 `<style>` 顶部写 `skin: <对象> UI`。报告该像那个产品的文档，不该像模板——但也不该失去结构的一致性。
3. **元信息**：固定六行标签表（对象 / 版本提交 / 报告版本 / 克隆 / 方式 / 日期），不压成 `·` 串。
4. **机器可读**：`<script id="report-meta">` 固定 schema + `index.json` 跨版本登记；报告同时给人读、给 agent 读。

正文结构（模板见 `assets/report-kernel.md`）：

`决策简报（7 行 + 3 KPI）` · `01 进入` · `02 安装后` · `03 核心链路（输入 / 处理 / 输出）` · `04 承载者` · `05 横切` · `附 证据` · `附 自证` · `附 参考`

**五幕是状态链，不是五个章节。** 功能挂在状态节点下面，一个功能只在一个主位置讲透，其他位置用 `#fn-N` 锚点。每一幕的摘要：

- **1 进入**：第一次怎么跑起来；宿主/平台、前置条件、安装/接入、第一条命令、第一个可见结果、卡点。
- **2 安装后**：环境多了什么；新增资产、被激活的能力、好影响、代价/坏影响、没变的东西、回滚。
- **3 核心链路**：输入落到最小单位；状态表 ≥3 行；输出可验证；功能档案 ≥6。
- **4 承载者**：每个阶段的 owner、state store、读/写、中断/恢复、清理。
- **5 横切**：影响矩阵四行（人/宿主/对象/产物）+ 未验证与待拍板。

**静态资产规则**：`SKILL.md`、配置、manifest、hook 脚本、模板、提示词，只有回答"谁读 / 改变哪个状态 / 没有它会怎样 / 证据在哪"才进正文；答不出就是资产清单里的一行，放证据附录或删掉。

深度下限：功能档案 ≥6；源码引用 ≥15 处且覆盖 ≥6 个文件（单文件产品可用 `research.singleFile: true`）；宣称/可见/实现表每行带代码引用或"无实现"；至少做一次口径对照；状态表 ≥3 行。

四件必须品 + 本版变化**全部放证据附录**，第一屏只留一句：

- **需求回归**（`appendix-selfproof`）：用户原话逐条打勾，状态只有 ✅ / ⏳ / ❌。
- **三段读者验收**（`appendix-selfproof`）：第一屏 7 问 / 五幕主线复述 / 证据 3 个事实复述；`[读者验收]` 必须写在正文，不能只写在注释里。
- **自我反驳**（`appendix-evidence`）：至少 3 条「先以为 → 更正 → 证据」。
- **非变更自证**（`appendix-selfproof`）：操作区间、写操作次数、被改动文件 mtime、关键计数前后一致。
- **本版变化**（`appendix-selfproof`）：v≥2 的 delta 块；首次写"首次调研，无上一版"。

再调研（v≥2）：逐条复检上一版的每个功能块，写「仍成立 / 已变化 / 未复查」，填进 `report-meta.research.recheck` 和「本版变化」块。**"结论未翻转"必须建立在重新验过之上**；上一版最硬的缺陷不许悄悄消失。

**校验器**：`node scripts/check_doc.mjs <file>`。v3 检查五幕、a3 子段、状态表、承载者表、证据附录、`[读者验收]`；v2 继续九段 + 可读性检查；legacy（无 `contractVersion`）只做九段结构检查。v2 报告若缺 v3 才新增的 `reader` / `brief`，只给 warn，不判失败，避免旧报告被误杀。交付前必须全绿（空脚手架允许"结构通过、内容待填"的预期失败）。

**台账注释**：C-007（先给大白话）/ C-018（先产品画像）已由 C-024 升级为交付闸门；C-025 明确源码调研是一等模式。

## 收尾（交付后问一次清理）

报告交付后追加一行提问，只问这一次：

> 报告已生成 `<path>`。要清理本次的临时文件与进程吗？报告、克隆的代码、源码一律不动。

用户说清就按三桶处理：

| 桶 | 内容 | 处理 |
|---|---|---|
| 保留 | 报告、`index.json`、克隆的仓库、源码 | **永不删除**，不问也不动 |
| 可清 | 本次创建的临时目录、截图中间文件、`_npx`/缓存条目、npm debug 日志、应用自建的数据目录与 DB、lock 文件 | 先列路径 + 大小，再删 |
| 必停 | 我启动的进程与端口；共享缓存（`_cacache`、pnpm store） | 先确认 0 监听 / 0 残留进程；共享缓存单独问 |

删前给清单（路径 / 大小 / 是什么），删后复测端口与存活文件。

## 矫正账本

`assets/correction-ledger.md` 是本 skill 的成长机制。用户每次纠正后追加一条（场景 / 我做的 / 纠正的 / 提炼规则 / 适用范围）。

- **命中两条才升级**：同类矫正出现两次，或用户明确说"记住"，才写进 SKILL.md 的硬规则；其余留在账本当案例。
- 每次开工先读账本，把相关条目应用到本次调研。
- 只在用户明确要求时更新账本，不改写历史条目。
