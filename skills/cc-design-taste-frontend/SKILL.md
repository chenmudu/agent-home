# tasteskill v2

模型做出来的页面，通常像是它见过的所有页面取的平均值：一个居中标题压在三行上，
上面一个小标签，一排图标卡片，一层柔和渐变，
几根细线，再加一行等宽字体写的说明。
里面没有一处是错的，也没有一处是被决定过的。

这个 skill 用四种方式，把那些默认换成了决策：

1. **脚本发牌给出方向，你在其中挑选。** 让模型自己发明一种外观，它每次都会选品类
   默认值。`scripts/draw.mjs` 从二十个经过研究的方向里发出三张牌；你挑其中能承载
   主题想法的那一张，脚本再从一份由 247 个真实站点提炼出的库里，发出它的字体
   系统、配色、首屏和各区块构图。
2. **想法来自主题本身。** 在那项研究里，最好的站点和记不住的站点之间的差别，是一个
   从事物本身取来的概念，而不是样式。
3. **一套没有装饰的自家风格，** 由 `scripts/inspect.mjs` 在真实浏览器里测量，规则
   因此是被检查的，而不是被指望的。
4. **你去看自己做出来的东西。** 三个宽度的截图，一份评审打分表，修，再看。

测试中学到一条警告。把装饰拿掉只是工作的一半；一个页面丢了标签、细线和卡片，却
没有任何东西补上它们的位置，读起来就是单薄，
盲评的评审也确实更有理由要一个带破绽但更丰富的页面，而不是一个没有破绽的空页面。
另一半是实质：字号设得更大，整片的色块，
这个主题世界里真实的图像（找来的或画出来的），以及每个区块都承载它完整的内容。
这个 skill 就是为了给你这些而建的；不要拿它去换克制。

下面的命令里，`<skill>` 指这个 skill 所在的文件夹。请从项目根目录运行，这样工作
文件会落在该目录下的 `.taste-skill/` 里。脚本需要 Node 22+ 以及已安装的 Chrome、
Edge 或 Chromium，不安装任何东西。`assets.mjs` 还需要网络访问；它不使用 API key。

## 页面还是应用界面

先判断这属于两类工作中的哪一类。

- **页面**是被阅读和滚动的：落地页、营销站或产品站、作品集、活动页、餐厅页、单页。
  它走下面的**流程**。
- **应用界面**是被人操作使用的：仪表盘、后台或分析视图、设置、账单、要逐条处理的
  收件箱或队列、钱包、带筛选的列表、编辑器或搭建器。它走 **`references/app-screens.md`**：
  它有自己的流程、自己的发牌（`draw.mjs --app`）、自己的自家规则（那里边框安静、
  小标签和重复面板是正常的；渐变、光晕、色块方块里的图标、彩虹图表和编造的虚荣
  数字则不是）以及 `inspect.mjs --app`。开始之前把那个文件整份读完；下面的页面流程不适用。

展示自家应用的产品站是一个页面；它上面的界面片段，内部按应用界面的规则走。产品的
应用风格只发一次牌，放在它自己的文件夹里，并保留页面的颜色和字体：

```bash
node <skill>/scripts/draw.mjs --app --kind <kind> --brief "<the product>" --keep palette,type --out .taste-skill/app
```

然后让页面展示的每个片段（首屏的实时界面、
某个功能的局部裁切、一张图表）都成为
那个应用真实的一部分：面板、表格和控件用 `assets/app.css`，图表用 `assets/charts.js`，
数据要真实且能对得上，只陈述一个结论，
按页面蓝图对待图片的方式来裁切和缩放。一个
看起来像在真正运行的产品片段，是软件页面能有的最强图像；灰色条和 lorem 占位数字
则是最弱的。当一个需求同时混了两者（一个落地页和它背后的仪表盘），各自按自己的
流程做，共用一套配色和一款字体。

## 流程

按顺序做。第 1–5 步只需几分钟，却决定这个页面好不好。

### 1. 读需求与项目

搞清楚什么是真实的：主题、受众、页面必须让某人做的那一件事、技术栈、已有的品牌
（颜色、字体、logo），以及最重要的——**真正存在什么图像**：项目自己的照片或产品图、
可以展示的真实界面、你能调用的图像生成工具，
或者什么都没有。不要围绕你手上没有的
图片做规划。它自己什么都没有，也很少等于真的一无所有：主题所在的城市、街道、材料
和历史都在开放档案和博物馆里，可以免费使用，
署名即可（第 6 步，`scripts/assets.mjs`）。

如果需求含糊，自己作决定，用一句话说明你的理解，而不是去问。只有当缺失的事实卡住了
工作（例如没有产品名）时才问。

然后在笔记里**给主题做一次清点**：八到十二件属于这个客户、不属于任何竞争者的事。
去找它的名字以及名字的含义；它的地址、
门牌号、街道和街区，以及那个地方长什么样
（它的瓷砖、招牌、涂料颜色、店面上用的字体、它的光线、它的天气）；需求里的数字
（座位数、房间数、到海边几分钟、价格、
年份）；它与生俱来的限制（一个月只做一批、
冬天歇业、只接受预约）；它的材料和颜色；
它的仪式和时刻（五点升炉火、七点的渡船）；
它那个世界里的印刷品（时刻表、标签、票、
标牌）。这份清单就是第 4 步里想法的来源。
在盲测里，每个需求胜出的页面都是从这样一份清单上的某一项建起来的（客户的名字和它
的含义、它所在的街道、让它成为它自己的那条限制），而落选的页面则是构图不错、但想法
停留在品类层面。这份清单同时就是你的图片搜索：上面的每个地点、材料和印刷品，都是
第 6 步的一次查询。

### 2. 写出论证

在任何设计之前，把页面列成主张及其证明，
每个区块一行，就像 `references/copy.md` §1
展示的那样。主张决定有哪些区块、以及它们的顺序。删掉任何没有主张的区块。这样你才
不会掉进首屏、logo 墙、三个功能、推荐语、定价、行动号召这套固定序列。

### 3. 发出方向

```bash
node <skill>/scripts/draw.mjs --sector <sector> --brief "<one line about the subject>" \
  --sections <roles in the order of your argument> [--tone <tone>] [--have <assets>] [--keep palette,type] \
  --options 3
```

这会发出三个方向，并为每个打印一段简短摘要。把每一个拿回你的清单上比对：哪一种构图
方式能承载只有这个客户才有的东西？选那一个，
不要选最眼熟的，并在笔记里写一行为什么。
测试中，一个随意发出、并不适合主题的方向，
是弱页面最常见的原因。然后发出完整的那张表：

```bash
node <skill>/scripts/draw.mjs <the same arguments, without --options> --direction <chosen id>
```

- `--sector`：`node <skill>/scripts/draw.mjs --list sectors`。选最接近的。
- `--sections`：来自 `--list roles` 的角色（features、showcase、how-it-works、testimonial、proof、
  stats、pricing、faq、cta、footer、intro、about、work、gallery、list、contact）。首屏是隐含的。
- `--tone`（可选）：quiet、bold、warm、technical、playful、luxury、editorial。只有需求明确
  要求某一种时才传。
- `--have`：真正存在的素材，逗号分隔：`photography`（项目自己拍的场所、人物或作品照片）、
  `product-photo`（具体产品的照片，或者一个能做出它们的图像工具）、`product-ui`（真实截图）、
  `illustration`、`video`。如果没有就不传：这样发牌会避开依赖它们的构图，表上也会说明
  如何诚实地填满图片位置（软件展示它自己用 HTML 做出来的界面；没有照片的产品会被画出来，
  放在它那个世界的真实图片之间，绝不用一张假的产品图）。你之后在开放图库里找到的图
  不属于项目自己；不要放进 `--have`。
- `--keep palette,type`：当品牌已经固定了颜色或字体时。这样发牌只发构图，你把品牌的
  值映射到各个角色上。

命令会打印一张**方向表**。它就是这次构建的艺术指导：

- **采用它。** 不要把它和你本来就会做的那种布局混在一起。如果它让你觉得陌生，很好：
  眼熟的那种布局，正是这个 skill 存在所要防止的。
- 只在你能说出理由时才重发某个槽位（`--redraw hero | type | palette | photos | scenes | section:<role> | direction`）：
  它与明示的品牌约束冲突、需要不存在的素材，或者是一个装不下真实内容的区块（见下一点）。
  永远不要为了更舒服而重发。每一次重发都记进报告。
- 当一个发到的区块装不下真实内容时（它要对比三种方案而这里只有一个价格；它要五条
  报价而一条都没有），不要弯折内容去迁就它。用 `--alternatives <role>` 列出其它选项，
  挑那个假设与内容相符的，用 `--redraw section:<role>=<id>` 换上。
- **拿配色对一遍主题。** 一套发到的配色既是一组颜色，也是一组比例（一个底色、一个
  墨色、一个强调色、若干色块）。如果它的颜色和主题自身的材料打架（泥煤威士忌配糖果
  粉彩、山中小屋配霓虹），重发一次配色；如果主题本身有不会认错的颜色（它的材料、
  它那条街的涂料、它窗外的风景），保留发到的比例，改从主题里取颜色，并在报告里说明。
- 随时可以用 `node <skill>/scripts/draw.mjs --show` 重新打印它。在长会话里，每建一个
  区块之前重读一遍。

### 4. 找到想法

方向是一种构图方式。想法才是让这个页面属于这个主题、而不属于任何别的东西的原因。
把这句话写进笔记，在两个空都从主题本身填上之前不要开始动手：

> 在这个页面上，**[属于这个主题的某样东西]** 变成 **[方向所要求的那个装置]**。

第一个空的寻找之处：

- **它的产出。** 这个东西生产什么？把真实产出当作材料放到页面上。（一台会打印
  诗句的相机，把它的文案以纸条的形式交付。）
- **它的物件或形状。** 它在物理上长什么样，剖面是什么样，剪影是什么样？把它放大、
  裁切，让它成为边框或唯一的主视觉母题。
- **它的名字。** 那些字母能不能装下一张照片、堆成一面墙、拆到两个角上？
- **它所在的地方。** 有没有一个视角，能让人想身临其境？
- **它的仪式。** 有没有一个序列，页面可以在滚动时把它演出来？
- **它的印刷物。** 它的世界里已经存在什么印刷品：票、菜单、标签、收据、请柬、
  文件夹、说明书？
- **它的反面。** 这个品类缺的那种感觉，正被哪一个别的品类占着？

第一个空要从你的清单（第 1 步）里填，不要从品类里填。**竞争者测试：** 把最近的那个
真实竞争者放进这句话里（两条街外的那家面包店、另一个做橡木家具的人、同一座山上的
另一间小屋）。如果这句话照样成立，那这个想法属于品类：一条面包是每一家面包店的；
以这条街命名的这七扇门，只属于这一家。"干净现代"不是一个想法。研究里评审打最低分的
那些站点，它们的想法被记录为"除了标准公式之外没有"。

**一件活的交互。** 给页面一件访客能做的事，
或者每次访问都不一样的事，由那个想法
做出来：选一种木料，看到用它做的椅子；
输入你的名字，看到它用铸造厂的字体刻出来；
设定贷款额度，读出真实的月供数字；看小屋的炉子此刻是否点着，以及离末班渡船还有
多久；选一个尺码，看它在房间里的样子。在盲测里，每一个胜出的页面都有这样一件东西，
评审们第一个就点出它。规则：它使用主题的真实内容，能用拇指在手机上操作，没有脚本时
有一个朴素的回退，它从不阻挡阅读，而且它只是一件事，不是游乐场。它在第 6 步作为
页面的一部分建出来，不是在第九步当作动效加上去。

**场景也承载想法。** 表上的滚动场景是一些等着主题来认领的装置。动手之前，从你的
清单里决定每一个展示什么：穿越镜头穿过的，
是这家工作室自己的片头卡；那条路线，是
这批货真正走的那条路；那张展开到整屏的图，
是客人醒来时会在的那个房间。一个装满
谁的图都能用的场景，就是一张屏保。

### 5. 写出文字

在写标记之前，先把整个页面写成一份文案稿（纯文本），遵循 `references/copy.md`：

- **每一个标题在每个宽度下都只占两行或更少。** 定下一句话之前，先算一遍 copy.md §2
  里的算术：在一个有底气的字号下，大约 32 个字符在任何地方都安全。被研究的图库首屏
  中位数是 5 个词、32 个字符。
- 一句支撑句，紧贴在标题下面（在它下方 32–48px），与标题一起展示，绝不压到首屏的
  底部，也绝不被动画延后。当标题是一个名字或一个修辞时，这句话要平实地说明这东西
  是什么。一个主要动作，以它做的事命名，在首屏上是一个真实的按钮。
- **首屏用大字号回答访客的第一个问题。** 对一个活动：它是什么、什么时候、在哪里
  （日期属于标题或第二字号，绝不能只出现在小字里）。对一个产品：它是什么，多少钱
  或做什么。对一个人：是谁，做什么。访客为之前来的每一个区块（阵容、菜单、房间、
  价格）都有自己的标题，在导航里有自己的位置。
- **写完整的内容。** 需求里要求的每个区块都要把信息交付完整：带价格的整份菜单、
  每个房间自己的细节、每一位讲者和每一场演讲、价格以及它包含什么、每一个真实问题
  都要有回答。单薄的区块，是一个干净的页面输给更热闹页面的最常见原因。
- 需求留白的地方，期望有示例细节（菜名、房间名和房价、项目标题），这样设计能在
  完整密度下被看到；把它们列进报告，让客户确认。证明永远不编造：没有客户、引语、
  评价、媒体报道、logo 或经营数据。

### 6. 把它建出来，静着建

在脑子里关掉动效来建这个页面；一个需要动画才显得完成的页面，就是没完成。工作顺序：

1. **Tokens。** 把表上的颜色和字体角色写成 CSS 自定义属性。往下的一切只引用 token。
   `<skill>/assets/base.css` 是一个你可以从其出发的中性基础（reset、token 名称、流体字号
   阶梯、栅格、焦点与选中样式、动效辅助类）；它本身没有任何外观。
2. **首屏，完全按照蓝图描述的样子，** 在桌面宽度和手机宽度上。在任何其它东西存在
   之前，先把大的做大、小的做小。
3. **每个区块都按它的蓝图，** 用这个项目的内容。保留几何结构，更换主题。相邻的区块
   不得共用一种布局。**把想法带进每一个区块，** 包括定价、FAQ 和页脚：研究里最常见的
   失败，即使是在好站点里，也是一个有辨识度的首屏，后面跟着一堆标配区块。
4. **图像，** 按这个优先顺序：
   1. 项目自己的；
   2. 生成的，如果你有图像工具；
   3. **来自开放图库的、主题世界的真实图片，** 只要存在一张诚实的。用
      `node <skill>/scripts/assets.mjs "<query>"` 搜索它们（Openverse、Wikimedia
      Commons、芝加哥艺术博物馆和 Met；默认只取允许商业使用的许可）。搜索清单，不要
      搜索品类：它那条街的老明信片、街区的一张老地图、它材料的一张特写、它这门手艺的
      版画、一件同类博物馆藏品、一页植物图版、一张星图。把它们用得大、用得有意：一张
      档案照片作首屏，一幅版画放大成页面的母题，那条街的真实地图作为联系区块。挑选
      之前每一张都要看；`--get <ref>` 会把它下载到 `assets/` 并记录来源与许可，
      `--credits` 会打印页脚要用的署名行。一张找来的图展示的是客户周围的那个世界，
      绝不被呈现为客户自己的产品、房间、菜品、人或团队；
   4. **用代码从主题本身画出来的，** 用于那些没有诚实图片可用的东西（它的物件、它的
      瓷砖、它的窗、它产品的界面，做成一门一致的扁平图形语言，用配色里真实的颜色）；
   5. 表上发到的照片，只用在诚实的通用图片合适的地方（海边的房子配海），绝不当作
      主题的替身；
   6. 只用字体和颜色。

   当项目有影像素材，或者有它自己流程或产品的真实图片时，首屏就展示它，大尺寸（约占
   屏幕 40% 或更多）。绝不要在页面上写一句话说明图片来自哪里、或者它们不是什么
   （"这些都不是我们的吧台"）：图注说明这张图是什么，署名行小字放在页脚。当一个作品
   集的作品是为需求虚构的，要把每一件都画成那件作品的完成定格画面（它自己的片头卡配
   它自己的字体、一个片尾帧、一张海报），带真实的细节，绝不能画成客户产品的象形图。

   **下限，由检查器检查：** 页面上至少有四张真实图片，通常是六到十二张（照片、档案
   图像、地图、版画、影像素材、位图作品；对软件来说，裁切过的界面片段也算）。SVG 画作
   不计入下限：没有图片可用的东西你画出来，同时仍然要带真实图片。只要有一段诚实的
   片段，就加一张会动的图：用 `assets.mjs --video "<query>"` 搜索，把它当作静音循环
   加一帧海报图来用。模型会跳过图片和影像，因为找到它们是要花力气的活；没有这些，
   页面就不合格。

   `references/imagery.md` 覆盖搜索、许可与署名、视频、绘制、裁切与处理。
5. 第 4 步的**那件活的交互**，建在它能证明主张的那个区块里（通常是首屏或预订），带
   真实内容、一个拇指大小的手机版和一个朴素回退。
6. **滚动场景，** 当表上发了它们时（第 9 节），每一个都连同它承载的区块一起做：页面
   的大时刻、穿过作品的相机、展开到整屏的那张图、在滚动下弯折的那个词。从
   `<skill>/assets/scenes/` 复制共享舞台和该场景的文件，用这个项目自己的图片和文字填
   充场景，并把页面的 token 设好，让它呈现页面的外观。场景是一种构图：它决定页面有多
   长、每一屏展示什么，所以它在现在就建，并且在每一轮看的时候都被看到，而不是最后才
   加上。`references/scenes.md` 说明怎样把一个场景放到页面上、填充它、让它贴合、以及
   检查它；`assets/scenes/demo/<id>.html` 是每一个场景的可运行示例。
7. **饱满。** 把每个桌面屏当成一张海报来看：一个占主导的东西，以及它承载的内容。一个
   大部分是空地的屏，是建得不够的区块，不是留白；每页一处刻意的留白就是上限，检查器
   会让有两个或更多近乎空屏的页面不合格。连续正文用完整的墨色，16px 或更大；灰色
   用于次要说明。
8. **外框。** 页面在每个宽度下都有一对相等的外边距，每个区块都使用页面已经立好的那个
   宽度：当它的文字在左半边，右半边就放它的图、它的第二栏、它的列表或它的图形，绝不
   什么都不放。不对称住在栅格内部，绝不落在外框上：只有远侧有东西收住它时，才放一个
   空。页面上没有一段比大约半屏更高却什么都不放的地方；桌面端区块之间相距 120–240px。
   访客为之前来的每个区块，都以一个点出它的标题开头，首屏用 `h1` 承载页面的标题。
   这些正是页面看起来不对劲时读者最先说出口的东西（"没有清楚的标题"、"莫名的空白"、
   "所有东西都挤在一边"），检查器对每一项都有测量。
9. **状态与语义。** 真实的链接和按钮、可见的焦点、alt 文本、一个自身就是一套构图的
   手机布局。每一个控件，包括那件活的交互，都要只靠键盘、按阅读顺序工作，并且有一个
   无障碍名称：它可见的标签，或者当它只显示一个图标时用 `aria-label`。

当你需要一个决定背后的细节时，读 `references/type.md`、`references/colour.md` 和
`references/layout.md`；下面的法则是简写版。

### 7. 关卡

```bash
node <skill>/scripts/lint.mjs <source files or folder>
node <skill>/scripts/inspect.mjs <url or path/to/index.html>
node <skill>/scripts/scenes.mjs <url or path/to/index.html>     # when the page has scroll scenes
```

`scenes.mjs` 在桌面端和手机上、以及减少动效的页面上，为每个滚动场景在它驻留时长的
0、10 … 100% 处拍照；当表上有场景时，`inspect.mjs` 还会把整段滚动拍成影片
（`desktop-film-NN.jpg`）。一个从未开始、
或者在桌面端静止不动的场景是 `FAIL`。

`lint.mjs` 扫描源码里违禁的模式和陈词滥调。`inspect.mjs` 在真实浏览器里以 1440、768
和 390 像素打开页面，对它做测量（标题行数、
字号、实际加载的字体、颜色、细线、阴影、
渐变、对比度、溢出，以及外框：边距是否相等、
区块是否挤在一边、有没有空白段、标题、
无标题的区块、文字是否贴着屏幕边缘），
并把截图存到 `.taste-skill/inspect/`。修好
每一个 `FAIL`。把每一条 `WARN` 都当作错的，
除非你能用一句话向一位设计师辩护它。
一直重跑到没有 `FAIL`。不要和量尺争辩，
也不要对它藏东西。检查器通过一个临时本地
服务器提供本地文件；如果页面还必须直接从文件系统打开，在结束之前用那种方式打开
一次 `index.html`。

检查访客实际收到的东西。有构建步骤时，在产物构建上跑最后这道关卡（`vite build && vite preview`、
`next build && next start`，或者构建出来的 `index.html`），不要只在 dev server 上跑：
压缩器和打包器会改变实际发出的东西（有一次，一个 `backdrop-filter`
在 dev server 上能显示，最终却被去掉了）。检查器在看着 dev server 时会给出警告。

### 8. 看

过关意味着没有测到违禁的东西。它不意味着页面是好的。打开检查器列出的截图（每一个
视口，用你的看图工具或 Read 工具），用 `references/critique.md` 去批评它们：那十四遍
检查、按 Awwwards 加权算出的分数、各类上限。按它的格式把批评写下来，修掉最严重的
三个问题，再跑检查器，再看一遍。最多三轮。

只凭图片判断。一个问题只要在截图里肉眼可见，它就是真的，不管代码怎么说。

### 9. 动

现在建动效层。它是必需的，而且不止一次淡入：
检查器会数页面加载和滚动时真正在动的
元素，少于八个的页面不合格（少于十六个会警告）。滚动场景已经建好了（第 6 步）；在
它们周围，这一层有四个部分：

1. 表上点名的**标志性动作**：一个，做好（一个发到的场景可以就是它）。
2. **每个区块各部分的入场：** 先标题，再文字，再图片，依次错开 60–90ms，带着透明度
   上升 16–32px，在区块进入视口时触发一次。不是整块一次淡入，也绝不能是脚本失败就
   永远藏着的内容。
3. **每个控件的反馈：** 按钮、链接、卡片和那件活的交互的按下、悬停与聚焦。
4. **一张会动的图：** 一段找来的片段作静音循环，一张照片上缓慢的缩放或漂移，或者
   首屏图片上跟随滚动的位移。

只用 transform 和 opacity；每一个动作都有一个 `prefers-reduced-motion` 回退，保留
内容、去掉位移。一个改变整屏颜色或布局的动作（按章节变色的、钉住的故事）属于构图的
一部分，所以在第 6 步就建它，让每一轮看的时候都能看到。`references/motion.md` 有
token 和经过测试的配方。然后再跑一次检查器，逐张查看截图，找没能出现的内容。

### 10. 汇报

在以下全部成立之前不要汇报；每一条，都在某次结果很糟的测试运行里被跳过过：

- `inspect.mjs` 在页面的最终版本上，1440、768 和 390 三个宽度都显示 **0 FAIL**。
- 你打开过最后一次改动之后它列出的每一张截图，不只是首屏。
- 有滚动场景时：`scenes.mjs` 在最终页面上跑过、没有问题，并且你读过每一张表（桌面、
  手机、减少动效）。
- 一个陌生人看首屏五秒钟，能说出这是什么、该做什么。
- 每个区块都有标题；两侧边距一致；页面上没有一段是空的。
- 你最后一轮的批评，按 `references/critique.md` §4 的形状写了下来。

简要地告诉用户：发到的方向（名字和种子）以及任何重发及其理由；那句想法和那件活的
交互；你最后一轮批评的最终分数，以及还有什么不够；每一张找来的图片和片段，连同它的
标题、创作者、许可和来源页（`assets.mjs --credits` 会打印清单），以及它的署名落在页面
上的什么位置；哪些内置照片、哪些画作是代替摄影的（这样它们可以被替换）；以及上线前
必须换掉的任何示例内容。不要声称跑过一个你没跑的检查。

## 自家规则

这些在每一次构建上都成立，无论方向是什么。`inspect.mjs` 会测量它们。

| 规则 | 改为 |
| --- | --- |
| **标题：在每个宽度下两行或更少。** 每一个 `h1`–`h6`，以及首屏的主行，不论它是什么标签。 | 先砍字。再放宽行宽。最后才调字号。 |
| **首屏上有一个清楚的标题**，放在页面唯一的那个 `h1` 里，并且每个区块都有标题。 | 说清楚这是什么：名字加上它做什么，产品加上它为谁而做，活动加上它的日期和地点。 |
| **相等的外边距；没有区块挤在一边**而另半边屏幕空着。 | 用远侧的某个东西收住每一个空：这个区块的图、第二栏、一个列表、一个图形。 |
| **没有空白段**高于大约半屏。 | 用正常的区块间距。刻意的留白是一张放好的图或一片色块，每页一次。 |
| **陈述句是段落。** 一句设得很大的引言或引语，用 `<p>` 或 `<blockquote>` 标记，保持在陈述句字号（桌面 36px 或更小，手机 24px），长度大约 25 个词、三行。 | 比这更大它就是标题，两行规则适用。盲测里，评审会把一句 42px、铺了四行的话读成一个四行的标题。 |
| **不要眉毛。** 标题上方不要小标签，标题上方不要胶囊徽章，不要 "New ·" 小片。 | 把信息放进标题或第一句里，或者干脆去掉。 |
| 真实代码块之外**不用等宽字体**。 | 用正文字体。数字要对齐的地方用表格数字（tabular figures）。 |
| **不要序号。** 不要 01 / 02 / 03，不要 (001)，不要 "Step 2"。 | 顺序靠位置、大小或文字本身来体现。顺序重要时用真正的 `<ol>`。 |
| **不要细线。** 不要发丝分割线，不要 1px 描边盒子，不要网格线、十字准星或裁切标记。 | 用空间。用背景色调的一级台阶。用尺度的变化。用一个实心形状。 |
| **不要渐变。** 不用作背景，不用在按钮上，不用在文字里。 | 用平涂颜色，或者一张真实照片。照片上的文字底下垫一层中性压暗是唯一的例外。 |
| **静止的东西上不要阴影。** 不要光晕。 | 表面之间用一级色调台阶。只有真正漂浮的东西才用阴影：一个菜单、一个对话框。 |
| **不要助手配色。** 不要奶油黄底色配赤陶色或铁锈色；不要紫色或靛蓝。 | 用发到的配色。 |
| **不要又小又全大写又拉开字距的标签。** | 用可读的字号、句首大写。 |
| **不要顶部带图标的功能卡片，不要一排排一模一样的卡片。** | 用发到的区块蓝图。 |
| **不要玻璃。** 不要背景模糊面板，不要漂浮的胶囊导航。 | 用一条朴素的条：字标、几个链接、一个动作。 |
| **不要 emoji，不要渐变色团，不要装饰性形状，不要灰色条拼成的假仪表盘。** | 一张真实图片、一个真实界面片段，或者什么都不放。 |
| 标题里**不要修饰过的强调词**（斜体、衬线、变色、加下划线）。 | 一款字体、一种颜色。让文字本身去强调。 |
| **最多两款字体，** 通常一款。 | 用发到的字体系统。 |

有三个地方保留自己的惯例，检查器不会去动：`<pre>`/`<code>` 里的真实代码（那里等宽
字体是对的）、真实的表格和表单字段（它们可以有线），以及根元素带有 `data-ui` 属性的
真实界面片段（产品自己的边框和菜单；见 `references/imagery.md` §7）。

说实话，为什么是这些。有些是研究测出来的：
在 247 个站点里，评审打 7.5 分及以上的
那些，使用图标功能卡片的比例是 1%，而 6.5 分以下的站点是 28%；胶囊徽章 14% 对 34%；
渐变 22% 对 52%；阴影 24% 对 48%；又小又拉开字距的全大写标题 16% 对 57%。另一些是
所有者本人的品味，并且与当下图库的流行相逆：
等宽标签、序号和发丝网格在获奖站点上
其实比在弱站点上*更*常见，这正是为什么生成器会模仿它们，也正是为什么它们现在读起来
像戏服。它们在这里被无条件禁止。`references/tells.md` 维护着这份带日期的登记表。

拿掉装饰会留下空间。绝不要用另一个装饰去填它。用尺度（把主要的东西做大）去填，用
完整的内容去填，用一张为这个主题做的图去填，
或者用一片平涂的色块去填。刻意留空，
每页最多一次。

## 手艺法则

简写版。数字来自那项研究，除非标注为自家风格。

**字体**
- 两到三个字号承担可见的工作：一个很大，一个小，中间没有。被研究站点的标题与正文
  字号比中位数是 4.3；最好的远超这个（最大字号：顶级站点中位数 8.4vw，弱站点 5.0vw）。
- 展示字体：字距 -0.02 到 -0.05em，行距 0.85–1.05。正文：16–20px，行距 1.45–1.6，
  每行 45–75 个字符。
- 一个页面最多五个字号。一款字族是常态（被研究站点的三分之一）；两款是上限。
- 默认左对齐。最多居中一个时刻。

**空间**
- 一套栅格、一对紧边距（16–32px），处处使用；大的东西顶到边缘。整页的文字块共用
  两到三条左边缘。
- 不对称在栅格内部，绝不落在外框上：两条外边距相等，一个偏离中心的标题，在栅格的
  远侧有东西与它呼应。
- 区块之间的间距明显大于任何一个区块内部的间距：桌面端 120–240px（研究的中位数约为
  240）。
- 每个区块的构图都与邻居不同；没有一个区块是卡片网格。

**颜色**
- 一个底色、一个墨色、一个强调色。强调色出现在动作上，也许再加一处别的东西。
- 连续正文用完整的墨色。通篇用柔灰色的页面读起来像没做完。
- 表面之间用色调的一小级台阶分隔，绝不用一条线或一层阴影。
- 一个区块可以改变整片底色。没有任何东西渐隐进另一个东西里。

**图像**
- 一张占主导的图胜过六张小图。在得分最高的站点上，首屏媒体有 68% 的情况覆盖了至少
  半屏。
- 相同的裁切比例、相同的处理、直角，除非方向另有说明（被研究站点的 73% 让媒体保持
  直角）。
- 没有图，好过一张占位图、一个图标或一个抽象形状。一张为这个主题画的、用它自己的
  颜色、认真画的图，比这两者都好。一张找来的、署了名的、它那个世界的真实图片，还要
  更好。
- 每一张找来的图都下载进项目、在页面上署名、并列进报告。没有一张被呈现为客户自己的。
- 绝没有任何东西压在标题或陈述句上（检查器会让它不合格）。

**组件**
- 按钮：平涂、一种填充色，要么直角要么全圆，一次定下（顶级站点：52% 直角，23%
  胶囊；9–16px 的"柔和"圆角是弱站点的默认）。大多数强有力的首屏根本没有按钮，或者
  只有一个。
- 导航：字标、三到五个朴素链接、一个动作。不要整条导航的装饰外壳。
- 一个控件靠它的形态、标签和位置来说明怎么用它。当它看起来需要一句话教人操作时，
  重新设计这个控件，而不是加上那句话。字段能接受什么，是另一回事。先尽量把限制去掉：
  用一个日期选择器，或者一个接受任何常见格式的解析器。仍然保留的限制，比如密码规则或
  文件类型和大小，就留在字段旁边可见，并用 `aria-describedby` 与它绑定。
- 页脚是一个设计过的收尾，不是站点地图：在大多数强站点上，名字以整幅宽度回归。

## 特殊情况

**已有的品牌或设计系统。** 传 `--keep palette,type`，把品牌的颜色和字体映射到各个
角色上，只从发牌里取构图。自家规则依然适用；
如果品牌本身要求一个被禁的装置（它的
logo 放在渐变上、它的强调色是紫色），保留品牌资产，在报告里说明，并且只针对那一条
规则给检查器传 `--allow <rule>`。

**已有的页面或应用界面。** 这个 skill 不处理已经在运行的界面。审查、清理、打磨、重设
样式或者给已有的页面或应用界面做红线标注，
属于 `cc-unslop` skill：它记录改动之前的
状态，保留内容、结构和技术栈，分几轮来做。开始上面的流程之前先转交过去。

唯一的例外是重建。当决定是丢掉当前布局、
按一个发到的方向重新组织各个区块时，就在
这里做——从流程的第 1 步开始，用页面的真实内容——并在报告里说明旧布局是被丢弃的，
而不是被修的。

**一个组件或单个区块，而不是一个页面。** 除非没有方向可循，否则跳过发牌。匹配周围的
设计，套用自家规则和法则，仍然要检查结果。

**没有结账、没有表单后端。** 当需求点名了一个真实目的地时，主按钮就去那里。否则它
打开一封写好了主题和正文的邮件（用 `mailto:` 并把访客的选择填进去）；如果是个商店，
它就指向 `#checkout`，报告里说明上线前必须接好。绝不做假的支付表单。

**没有 Chrome 或 Node 22。** 跑 `lint.mjs`（Node 18+），用你手上任何浏览器工具截图，
然后批评这些截图。在报告里说明检查器没能运行。

**没有网络。** 如果 `assets.mjs` 连不上任何来源，就自己画图，并在报告里说明开放图库
没能搜索。

| 文件 | 何时读它 |
| --- | --- |
| `references/app-screens.md` | 任何仪表盘、后台、设置或其它应用界面：它自己的流程、规则、token 和检查。 |
| `references/copy.md` | 写论证和文案稿时（第 2 步和第 5 步）。两行的算术。 |
| `references/type.md` | 设字体：阶梯、字距、行宽、加载字体、搭配。 |
| `references/colour.md` | 应用配色：角色、比例、色调台阶、深色页面、对比度。 |
| `references/layout.md` | 栅格、边距、节奏、区块的多样性、导航、页脚、手机构图。 |
| `references/imagery.md` | 挑选、寻找、署名、裁切和处理图片；一张都没有时怎么办。 |
| `references/motion.md` | 第 9 步。预算、token、配方、减少动效。 |
| `references/scenes.md` | 第 6 步，当表上发了滚动场景时：把一个场景放到页面上、填充、贴合、手机端、检查、目录。 |
| `references/critique.md` | 第 8 步。怎么看、怎么打分、先修什么。 |
| `references/tells.md` | 生成页面破绽的带日期登记表，以及每一条被什么替代。 |
| `references/research.md` | 那项研究：方法、数字、最好和最差的站点各自怎么做。引用它，不要猜。 |

| `scripts/assets.mjs` | 第 6 步：在开放图库里搜索主题世界的真实图片；`--get` 连署名一起下载，`--credits` 打印它们。 |
| `scripts/lint.mjs` · `scripts/inspect.mjs` | 关卡。 |
| `scripts/scenes.mjs` | 滚动场景的关卡：每个场景在驻留时长的 0-100%、桌面、手机、减少动效。 |
| `assets/base.css` · `assets/base.js` | 一个可选的中性基础，可在其上构建。 |
| `assets/scenes/` | 滚动场景：共享舞台（`stage.js`、`stage.css`），以及库里每个场景的 `.js`、`.css` 和 `demo/` 里一个可运行的示例页。 |
| `assets/app.css` · `assets/charts.js` | 用于应用界面：一个中性外壳、面板、表格和控件，以及按应用规则画的小型 SVG 图表。 |
| `library/` | 发牌读取的数据：方向、首屏、区块、字体系统、配色、照片、被研究的站点、动效、滚动场景（`scenes.json`），以及应用风格、外壳和屏幕模式（`app.json`）。不要整份读它；用脚本。 |
